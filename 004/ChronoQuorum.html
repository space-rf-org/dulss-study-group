A protocol you could build
ChronoQuorum
Ordering events with a clock instead of a leader — the whole idea, and the three bugs you will hit building it.
30 minutes. No prior consensus-protocol knowledge assumed.
The problem
You have sorted events by timestamp. It went wrong.
sensor node
obstacle detected
10:00:00.000
control node
turn left
10:00:00.004
your log
turn left obstacle detected
Either the clocks were 8 ms apart, or the first message queued behind the second. Now your log says the vehicle turned before it saw anything.
The usual answer: stop trusting clocks. Elect one node to number every event, and make everyone else follow it. That's Raft, and it works — it just costs you the election.
The idea
Postmarks
1
Everyone stamps their own letter, with their own watch.
2
All the watches agree — to within an error you know.
3
The mail takes at most a time you know.
4
Everyone sorts by postmark — and gets the same order, with nobody in charge.
Note what is doing the work: not that the watches are accurate, but that their error is known.
The idea
One catch, and one fix
The catch
A letter postmarked 10:00 can land after one postmarked 10:05.
Sort them as they arrive and two people end up with different orders. Which is exactly the bug from two slides ago.
The fix
Before you act on a letter, wait.
Wait longer than watch error + slowest mail. After that, anything postmarked earlier has definitely landed. So you can act.
That wait is the entire protocol. Everything else in this talk is bookkeeping around it.
The idea
"But the clocks are still a bit wrong"
Clock error cannot break agreement
Stamps are data. The number travels with the event, so every node sorts the same stamps by the same key — ties on node id. Nobody re-reads a clock at sort time.
What it does bound is meaning
Events further apart than the error cannot invert. Events closer than it are genuinely concurrent — you get one agreed order, not the true one. At 20 ns, that is a narrow window.
So the two terms in the wait do different jobs
Network delay — everything earlier has arrived, so your set is complete. Clock error — no node can still mint a stamp below yours. It closes the set against the future; it does not correct the sort.
A leader's log is arbitrary against real time at any separation — whatever order requests happened to reach it. Only the clock-ordered version can quote a number.
The rule
Sort by timestamp. Act only once nothing earlier can still arrive.
If you can bound your clock error and your network delay, you do not need a leader. If you cannot, you do.
How it works
What one node actually does
01 stamp
Read your clock. Tag the event with that time and your node id.
02 send
Broadcast it to every other node. No node is special.
03 ack
Everyone who receives it says "got it" to everyone.
04 commit
Once a majority acked and the wait has passed, append it.
The acks are not about ordering — the clock already did that. They tell you a majority actually has the event, so you are not acting on something that could be lost.
How it works
What it banks on
Disciplined participants
Every node runs the same rule and acks what it receives. None freelances, and none lies about its clock.
Uniform nodes
Same hardware, same build, same settings. Whatever the slowest node can do is what the cluster can do.
A deterministic network
Time-Sensitive Networking: scheduled, with a delay bound you can look up — not a network that is merely usually fast.
None of this was ordinary ten years ago. Precise time and scheduled networking are now stock hardware — this design simply spends what the hardware already gives you, instead of leaving it on the table.
Going fast is easy. Going fast together is the job.
A node that races ahead on its own has not gone fast — it has gone inconsistent. And inconsistent state means nothing at all.
How it works
How long to wait
wait = clock_error + max_network_delay + margin
clock_error
~20 ns
Measured, PTP on a wired LAN. Read it live from the daemon — never hardcode it.
max_network_delay
tens of µs
From your switch's traffic schedule if you have one, else a measured worst case.
margin
2×
A judgement call. On our numbers the margin, not the clock, is the biggest term.
On a wired LAN that lands at 50–100 µs. On a WAN with NTP it is tens of milliseconds — and your commit latency is the wait. That is the whole story of where this design fits.
How it works

B received the later event first. It still committed the earlier one first — because it waited. No node asked another node anything.
How it works
The commit rule, in full
loop:   p = smallest uncommitted event, by (timestamp, node_id)   if p is none:                                break   if acks(p) < majority:                  break   if any live clock < p.time + wait: break   append(p)
Six lines, and no leader to ask. Note the breaks: if the smallest event cannot commit, nothing later can either — so you stop, you do not skip ahead. Skipping ahead is bug number two.
How it works
When the clock gets worse
Get slower
Clock error rises, so the wait grows. Commits take longer. Still correct. This is the normal case and it needs no decision from anyone.
Go read-only
Past a ceiling you pick — say 10 ms — stop accepting writes. Drain what is pending. Reads keep working.
Stop
Majority unreachable, or time lost entirely. Halt and raise an alarm. Recovery is a human decision, not an automatic one.
There is no fallback protocol. One code path that gets slower is far easier to get right than two code paths that switch.

Compared with
What one ordered log gives you free
A message bus
Publish is a commit. Deliver is a read in commit order. Already ordered, already exactly-once — so no broker, no dedup table, no sequencer.
An audit trail
One log replays to exactly one history. Your runtime state, your telemetry and your incident forensics are the same bytes — they cannot disagree.
Aligned sensor data
Every event already sits on one timeline, so fusion and filtering need no per-source skew correction. Misalignment is removed at the source.
None of these are features we added. They fall out of having one time-ordered log instead of a database, a broker and a tracing pipeline that each keep their own clocks.
Compared with
Clocks keep getting better. Only one design collects it.
Raft, Paxos, VSR
The clock is only a timeout
Give them a perfect clock and they notice a dead leader sooner. They never commit a single thing faster. The clock is a failure detector and nothing else.
Here
The wait is the clock error
Halve the error and you halve the wait. The error already dropped five orders of magnitude when we moved from NTP-class to PTP-class time — with no change to the rule.
Cheap atomic clocks and better PTP keep arriving. For this design that is a protocol upgrade. For everything else on the previous slide it is a monitoring upgrade.
Building it
Five things you need first
1
A clock that reports its own error bound. PTP, not NTP — you need the number, not just the sync.
2
A network delay you can bound. A wired LAN you control, ideally with traffic shaping.
3
Fixed membership, 3 to 7 nodes. No dynamic joins — there is no reconfiguration story here.
4
Crash faults only. A node that lies about its clock breaks this, and detecting that is a different protocol.
5
A workload that would rather stop than guess.
Miss any one of the five and you should use Raft. That is not false modesty — it is the actual precondition list.
Building it
Three bugs you will hit. All three bit us.
1 · Committing before everything earlier has landed
A fast node commits the later event while an earlier one is still in flight. The wait must cover every earlier event, not just this one. A model checker found this before our hardware did.
2 · Advancing your watermark past a gap
A node that was down receives a live event from past its gap, commits it, and moves its "I have everything up to here" marker over records it never got. Silent, permanent hole. Fix: while catching up, drop live events and fetch the gap in order.
3 · The full-buffer wedge
A slow node's receive buffer fills, it drops an event un-acked, and the cluster stalls forever waiting for an ack nobody will send. Fix: never let a sender run more than N events ahead of the slowest node.
Building it
Do not use this if
—
Your nodes sit in different datacenters. Clock error becomes milliseconds, and the wait becomes your latency.
—
Membership changes. Nodes joining and leaving is not solved here.
—
You need more throughput than one core can serialize. We measure ~16k commits/s per node: one global order means one serializer.
—
You would rather be up and wrong than down and honest.
The sweet spot is narrow on purpose: a small fixed cluster, one good network, latency you must bound rather than average, and nobody on site to fix it.
Where this is
Honestly
Works

Specified, not built

To take away
Sort by timestamp. Wait out the uncertainty. Stop when you cannot bound it.
If you can bound your clock error and your network delay, you do not need a leader.

ChronoQuorum — nobody is in charge
Node A
Node B
Node C
1  A writes down the time from its own clock
2  A sends it to everyone
3  Everyone tells everyone "got it"
4  Everyone waits — long enough that nothing older can still turn up
5  All three commit, in clock order
One round trip, and no node ever asks another node a question. Every arrow is a statement, never a request.

A — wants to propose
B
C
1  A asks everyone: "may I propose, using ticket #5?"
2  B and C: "yes — and here is anything I already accepted"
3  A: "then accept value V, with ticket #5"

Two round trips. And the rule that makes it safe: if anyone in step 2 reports an already-accepted value, A must propose that one — not its own.

Raft — everything through one node
Leader
Follower 1
Follower 2
1  The client asks the leader — only the leader may be asked
2  The leader writes it down first, in its own list
3  "Copy this into your list, right after entry 11"
4  Followers copy it and say "ok"
5  Leader counts a majority, commits, answers the client
6  The next message tells the followers it is committed
One round trip — but every arrow starts or ends at the leader. If it dies, nothing moves until a new one is voted in.

Viewstamped Replication — the same shape as Raft
Primary
Backup 1
Backup 2
1  The client asks the primary — only the primary
2  The primary gives it the next number in the queue
3  "Prepare — write this down as number 12"
4  Backups reply "prepare-ok"
5  Primary counts a majority, commits, answers the client
6  A later message tells the backups it is committed
The difference is the handover. Raft votes, and only an up-to-date node can win — so no repair follows. VSR's next primary is fixed by rota, so it may be behind and must gather the others' lists.
